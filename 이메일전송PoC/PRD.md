# PRD — 망분리 환경 이메일 → 내부망 원클릭 전송 PoC

- 작성일: 2026-07-07
- 상태: 초안 (사용자 검토 대기)
- 유형: 개념 검증(PoC) 샘플 시스템

---

## 1. 배경과 문제 정의

회사 시스템은 내부망과 외부망으로 이원화되어 있다. 외부에서 받은 이메일의 본문과 첨부파일을 내부망으로 가져오려면 매번 다음 절차를 거쳐야 한다.

1. 외부망 이메일 접속 — 사번 + OTP 입력
2. 첨부파일을 수동으로 내려받기
3. 자료전송 시스템 접속 — 사번 + OTP **재입력**
4. 파일을 자료전송 시스템에 업로드하여 내부망으로 송부

**문제점**

- 이메일 1통을 내부로 가져오는 데 인증 2회, 수동 단계 4회가 필요하다.
- 메일 본문은 파일이 아니므로 별도로 복사하거나 캡처해야 한다.
- 반복 업무일수록 누적 시간 손실이 크다.

**개선 아이디어**

이메일 시스템 자체에 "메일 본문 + 첨부파일을 하나의 패키지로 묶어 자료전송 통로로 바로 보내는 기능"을 내장한다. 사용자는 이메일 로그인(사번+OTP 1회) 이후 버튼 하나로 전송을 끝낸다.

## 2. PoC 목표 (검증 포인트)

이 PoC는 다음 두 가지가 기술적으로 가능함을 증명한다.

1. **원클릭 패키징 전송**: 메일 본문 + 첨부파일을 표준 패키지(ZIP + 매니페스트)로 자동 생성하여, 버튼 하나로 망 경계 너머로 전달할 수 있다.
2. **인증 1회 경험**: 이메일 로그인 이후 전송 과정에서 어떤 추가 인증도 요구하지 않는다. 요청자 식별은 로그인 세션의 사번이 매니페스트에 자동 기록되는 것으로 해결한다.

## 3. 비목표 (Won't)

이번 PoC에서 명시적으로 제외하는 범위:

- 아웃바운드(내부 → 외부) 전송
- 실제 메일 송수신 (IMAP/SMTP 연동)
- 실제 OTP 검증, 실제 보안검사 엔진
- 인증 토큰 전달·검증 (로그인은 모의 화면으로 1회만 재현)
- 다중 사용자, 권한 관리, 운영 배포

## 4. 시스템 구성

하나의 프로젝트 안에 **두 개의 독립된 앱**과 **파일 기반 단방향 전송 통로**로 구성한다.

```
┌─ 외부망 웹메일 앱 (포트 3000) ─┐         ┌─ 내부망 포털 앱 (포트 4000) ─┐
│  · 사번+OTP 로그인 (1회, 모의)  │         │  · 전송 승인 대기함            │
│  · 받은편지함 (샘플 메일 시딩)   │  전송통로  │  · 보안검사 (모의 자동검사)     │
│  · 메일 상세 + 첨부파일 보기     │ ──────▶ │  · 승인/반려 처리             │
│  · [내부망으로 보내기] 버튼      │ (폴더 기반│  · 수신함 (본문+첨부 열람)     │
│  · 전송 상태 추적               │ 저장 후   │  · 처리 결과 회신             │
└───────────────────────────┘  전달)   └───────────────────────────┘
```

### 4.1 설계 원칙

- **단방향 통로 하나만**: 외부망 앱은 전송 통로(전용 폴더)에 패키지를 쓰는 것 외에 내부망 앱과 어떤 연결도 갖지 않는다. 실제 망분리에서 자료전송 시스템이 유일한 통로인 구조를 재현한다.
- **저장 후 전달(store-and-forward)**: 패키지가 통로에 저장되는 순간 전송은 완료된 것이다. 내부망 앱이 꺼져 있어도 패키지는 통로에 보존되며, 내부망 앱이 켜지면 자동으로 수거하여 처리한다. (실제 자료전송 시스템의 동작 방식과 동일)
- **상태 회신도 통로로**: 내부망의 처리 결과(검사중/승인대기/완료/차단/반려)는 통로의 상태 파일을 통해 외부망 앱에 반영된다. 직접 연결은 없다.

### 4.2 기술 스택

- Node.js + Express (두 앱 모두)
- 데이터 저장: JSON 파일 (데이터베이스 없음)
- 화면: 순수 HTML/CSS/JS (빌드 과정 없음)
- 실행: 터미널 명령어 하나로 두 앱 동시 기동 (Mac 로컬)

## 5. 패키지 포맷

[내부망으로 보내기] 클릭 시 생성되는 전송 단위.

```
package_<전송ID>.zip
├── manifest.json      ← 메타데이터
├── body.html          ← 메일 본문
└── attachments/       ← 첨부파일 원본
    ├── 보고서.pdf
    └── 사진.jpg
```

`manifest.json` 필수 필드:

| 필드 | 설명 |
|------|------|
| transferId | 전송 고유 ID |
| requesterId | 요청자 사번 (로그인 세션에서 자동 기록) |
| mailSubject | 메일 제목 |
| mailFrom | 발신자 |
| mailReceivedAt | 메일 수신 일시 |
| requestedAt | 전송 요청 일시 |
| attachments | 첨부파일 목록 (파일명, 크기) |

## 6. MoSCoW 기능 분류

### Must — 없으면 PoC가 성립하지 않음

| # | 기능 | 앱 |
|---|------|-----|
| M1 | 사번+OTP 모의 로그인 (웹메일 접속 시 1회) | 외부망 |
| M2 | 받은편지함: 첨부파일 있는 샘플 메일 5~6통 시딩, 목록/상세 보기 | 외부망 |
| M3 | [내부망으로 보내기] 버튼: 본문+첨부 ZIP 패키지 자동 생성 | 외부망 |
| M4 | 파일 기반 단방향 전송 통로 (저장 후 전달) | 통로 |
| M5 | 모의 보안검사: 패키지 수거 시 자동 검사 (금지 확장자·크기·매니페스트 무결성) | 내부망 |
| M6 | 승인 대기함: 도착 건 목록, 승인/반려 버튼 | 내부망 |
| M7 | 수신함: 승인된 패키지의 본문 열람 + 첨부 다운로드 | 내부망 |

### Should — PoC 설득력을 크게 높임

| # | 기능 | 앱 |
|---|------|-----|
| S1 | 전송 상태 추적: 내 전송 건의 현재 단계 표시 (전송됨→검사중→승인대기→완료/차단/반려) | 외부망 |
| S2 | 차단 시나리오: 금지 확장자(.exe) 첨부 샘플 메일 시딩 → 보안검사 차단 시연 | 양쪽 |
| S3 | 전송 이력 로그: 누가·언제·무엇을 보냈는지 기록 화면 | 내부망 |

### Could — 여유가 있으면

| # | 기능 |
|---|------|
| C1 | 첨부파일 선택 전송 (일부만 골라서) |
| C2 | 승인자 알림 배지 (새 요청 도착 표시) |
| C3 | 승인 전 패키지 내용 미리보기 |

### Won't — 3장 비목표와 동일

**MVP 범위 = Must 전체(M1~M7) + S1, S2.** 상태 추적과 차단 시연은 데모 효과가 커서 실질적 목표에 포함한다.

## 7. 핵심 흐름 (시연 시나리오)

시연은 브라우저 탭 2개(왼쪽: 외부망 웹메일 :3000, 오른쪽: 내부망 포털 :4000)로 진행한다.

### 7.1 정상 흐름

1. **로그인 (인증 1회)** — 웹메일에서 사번+OTP 입력. 이후 어떤 단계에서도 재인증 없음
2. **메일 확인** — 받은편지함에서 첨부파일 있는 메일 열람
3. **원클릭 전송** — [내부망으로 보내기] 클릭 → ZIP 패키지 생성 → 통로에 저장 → "전송 요청 완료" 표시 (이 시점에 외부망의 역할은 끝)
4. **보안검사 (자동)** — 내부망 앱이 통로에서 패키지 수거 → 형식·크기·금지 확장자·매니페스트 검사 → 통과 시 승인 대기함 등록
5. **승인** — 내부망 포털에서 승인자가 요청 내용 확인 → [승인]
6. **수신 확인** — 내부망 수신함에서 메일 본문 열람, 첨부 다운로드
7. **상태 확인** — 웹메일 전송 현황에서 해당 건이 "완료"로 표시

### 7.2 차단 흐름

.exe 첨부가 포함된 샘플 메일 전송 → 4단계 보안검사에서 자동 차단 → 웹메일 상태가 "차단됨 (사유: 금지 확장자)"로 표시

### 7.3 반려 흐름

승인자가 [반려] + 사유 입력 → 웹메일 상태가 "반려됨 (사유 표시)"로 갱신

### 7.4 내부망 앱이 꺼져 있는 경우

3단계까지 정상 진행되고 패키지는 통로에 보존된다. 내부망 앱을 나중에 켜면 자동 수거되어 4단계부터 이어진다. (저장 후 전달 검증 시나리오)

## 8. 상태 모델

전송 건은 다음 상태를 순서대로 거친다.

```
전송됨 ──▶ 검사중 ──▶ 승인대기 ──▶ 완료
              │              └──▶ 반려
              └──▶ 차단
```

| 상태 | 의미 | 전이 주체 |
|------|------|----------|
| 전송됨 | 패키지가 통로에 저장됨 | 외부망 앱 |
| 검사중 | 내부망 앱이 수거하여 보안검사 진행 | 내부망 앱 (자동) |
| 승인대기 | 검사 통과, 승인자 처리 대기 | 내부망 앱 (자동) |
| 완료 | 승인되어 수신함에 등록됨 | 승인자 |
| 차단 | 보안검사 탈락 (사유 기록) | 내부망 앱 (자동) |
| 반려 | 승인자가 거부 (사유 기록) | 승인자 |

## 9. 보안검사 규칙 (모의)

| 규칙 | 차단 조건 |
|------|----------|
| 금지 확장자 | .exe .bat .sh .js 등 실행 파일 포함 시 |
| 크기 제한 | 패키지 총 50MB 초과 시 |
| 무결성 | manifest.json 누락·필수 필드 결손·ZIP 손상 시 |

## 10. 화면 목록

### 외부망 웹메일 (:3000)

1. 로그인 — 사번 + OTP 입력 (모의: 형식만 확인)
2. 받은편지함 — 메일 목록 (첨부 여부 아이콘 표시)
3. 메일 상세 — 본문 + 첨부 목록 + **[내부망으로 보내기]** 버튼
4. 전송 현황 — 내 전송 건 목록과 상태

### 내부망 포털 (:4000)

1. 승인 대기함 — 도착 건 목록, 요청자·제목·검사 결과 표시, 승인/반려
2. 수신함 — 승인 완료 건 목록, 본문 열람 + 첨부 다운로드
3. 전송 이력 — 전체 처리 기록 (S3)

## 11. 에러 처리

- 패키지 손상·매니페스트 누락 → 보안검사에서 차단 처리 (사유 기록)
- 금지 확장자·크기 초과 → 보안검사에서 차단 처리 (사유 기록)
- 내부망 앱 미기동 → 오류 아님. 패키지는 통로에 보존되고 기동 시 자동 수거

## 12. 테스트 전략

- **자동 테스트 3영역**: ① 패키징 (ZIP 구조·매니페스트 생성) ② 보안검사 규칙 (통과/차단 판정) ③ 상태 전이 (허용된 전이만 발생)
- **수동 확인**: 7장 시연 시나리오(정상·차단·반려·미기동)를 체크리스트로 검증

## 13. 성공 기준

PoC는 다음을 모두 시연할 수 있으면 성공이다.

1. 로그인 1회 이후 재인증 없이, 버튼 클릭 한 번으로 메일 본문+첨부가 내부망 수신함에 도착한다
2. 금지 확장자 첨부는 자동 차단되고 사유가 외부망 쪽에 표시된다
3. 내부망 앱이 꺼진 상태에서 보낸 패키지가, 앱 기동 후 정상 처리된다
4. 두 앱 사이에 전송 통로 외의 어떤 직접 연결도 없다 (코드로 확인 가능)
