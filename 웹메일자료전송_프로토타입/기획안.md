# 웹메일 자료전송 프로토타입 — 기획안

## 문제
업무망·외부망이 분리된 환경에서, 메일로 받은 첨부파일을 업무망으로 넘기려면 파일을 다운로드한 뒤 별도의 자료교환 프로그램에 다시 업로드해야 하는 이중 작업이 반복되어 시간이 낭비된다.

## 개발 목표 (MVP)
3일 안에 만드는 첫 버전은 **실제로 동작하는 시스템이 아니라, 동료들의 반응을 확인하기 위한 클릭스루(click-through) 프로토타입**이다.

- 실제 파일 전송, 데이터베이스 저장, 로그인 인증은 구현하지 않는다 (가짜 데이터로 화면 흐름만 재현).
- 기존 자료교환 프로그램은 그대로 두고 건드리지 않는다. 이번 결과물은 그것을 대체하는 게 아니라 "이런 기능이 웹메일에 있으면 어떨지" 보여주는 데모다.
- 외부 CDN·서버 의존 없이, 단일 HTML 파일을 로컬에서 더블클릭으로 열어볼 수 있어야 한다 (망분리 환경 고려).
- 성공 기준: 동료가 파일만 받아서 열어봤을 때, 클릭 몇 번으로 "선택 → 신청 → 상태확인" 흐름을 오해 없이 따라갈 수 있는가.

## 화면
| 화면 | 역할 |
|---|---|
| A. 메일 읽기 (기존 웹메일 + 체크박스 추가) | 첨부파일 중 전송할 파일 선택 |
| B. 전송 신청 (모달) | 선택 파일 확인 + 반입사유·자료내용 필수 입력 + 제출 |
| D. 내 전송함 (좌측 사이드바 "확장 기능" 그룹) | 파일명 / 상태(승인대기·완료·반려) / 신청일시 리스트 |
| E. 반려 상세 (모달) | D에서 반려 건 클릭 시 반려 사유 확인 |

**화면 이동 흐름**
```
A(첨부파일 체크) --[업무망 자료전송 버튼]--> B(모달: 사유 입력)
      --[보내기]--> 자동 이동 --> D(내 전송함)
                          --[반려 항목 클릭]--> E(반려 사유)

D는 좌측 사이드바 "내 전송함" 메뉴로 언제든 단독 진입 가능
```

## 역할 (비개발자 3명, 화면별 분담)
| 담당 | 화면/작업 |
|---|---|
| 팀원 1 | A 화면 — 기존 메일 UI 재현 + 체크박스, 선택 상태에 따른 버튼 활성화 로직 |
| 팀원 2 | B 모달 — 파일 목록 표시, 필수 입력 검증, 제출 시 D로 데이터 전달 |
| 팀원 3 | D+E 화면 — 상태 리스트 렌더링, 반려 상세 팝업, 전체 색상·폰트 통일 및 최종 통합 |

## 협업 방식
**화면별 분담**을 기본으로 하되, 아래 규칙을 지킨다.

- Day 1 오전: 셋이 같이 공통 요소(색상 변수, 상태값 이름 — 승인대기/완료/반려, 화면 전환 함수 `goTo()`의 사용법)를 먼저 합의하고 문서화한다. 이후 이 이름들은 임의로 바꾸지 않는다.
- 각 화면은 더미 버튼/링크로 먼저 연결해두고, 그 다음 내용을 채운다 (화면 이동이 끊기지 않게 먼저 뼈대부터).
- 매일 마지막 30분은 셋이 함께 A→B→D→E 전체 흐름을 처음부터 클릭해보며 통합 테스트한다.
- 코드는 한 파일(`자료전송_프로토타입.html`)에 합치므로, 서로 다른 시간에 병합할 때는 각자 담당 영역(주석으로 구분된 `<!-- SCREEN A -->` 등) 밖은 건드리지 않는다.

## 사용 기술
| 항목 | 선택 | 이유 |
|---|---|---|
| 마크업/스타일 | HTML + CSS (인라인/내부 스타일) | 별도 빌드 도구 없이 파일 하나로 완결, 비개발자도 구조 파악 쉬움 |
| 동작 로직 | 순수 JavaScript (프레임워크 없음) | React 등 빌드 환경 불필요, 로컬 파일로 바로 실행 |
| 외부 리소스 | 사용하지 않음 (아이콘도 텍스트/이모지로 대체) | 망분리 환경에서 인터넷 연결 없이도 완전히 동작해야 함 |
| 제작 보조 도구 | v0.dev, Lovable, Claude Code 등 AI 코딩 툴 | 비개발자가 프롬프트로 화면을 생성/수정, 코드를 몰라도 스타일 조정 가능 |
| 배포 | 단일 HTML 파일 전달(메일/메신저) + GitHub(버전관리, private) | 실사용자 접근이 아니라 반응 테스트가 목적이므로 별도 호스팅 불필요 |

## 실제 구축 시 검토 필요한 기술사항 (프로토타입 이후 단계)

위 "사용 기술"은 어디까지나 데모용이며, 실제로 이 기능을 사내 시스템에 구축하려면 아래 항목들이 별도로 결정·검토되어야 한다. 현재는 대부분 **미결(open)** 상태다.

| 항목 | 현재 상태 | 비고 |
|---|---|---|
| **파일이 실제로 망을 넘는 방법** | **미결** | 후보는 ①벤더(자료교환 프로그램 제조사)에 API/폴더감시 기능 추가 요청 ②사내 IT팀이 자체 연동 서버 구축 두 가지. 이번 기획 단계에서는 확정하지 않고 다음 단계 검토 항목으로만 명시 |
| 사내 표준 기술스택 | **확인 필요** | 프론트/백엔드 언어·프레임워크가 IT팀 지정 표준을 따라야 하는지 아직 모름 → 실제 개발 착수 전 IT팀에 문의 필수 |
| 인증/SSO | 미결 | 사번 기반 자체 인증인지, 회사 SSO 연동인지 |
| 데이터베이스/서버 인프라 | 미결 | 망분리 환경 특성상 외부 SaaS 사용 불가 가능성 높음 → 사내 인트라넷 서버 필요 여부 확인 |
| 승인 로직 백엔드 | 미결 | 승인대기/사전승인/사후일괄승인 상태 전이를 처리하는 실제 로직 설계 필요 (기존 자료교환 프로그램의 승인 정책과 정합성 유지) |
| 보안 검토 | 미결 | 사내 보안성 심의 절차 대상인지, 첨부파일 임시 저장 위치·암호화·보관기간·삭제정책 |
| 감사/로깅 | 미결 | 승인/반려 이력, 전송 기록의 감사 추적(audit trail) 요구사항 |
| 웹메일 통합 방식 | 미결 | 벤더 웹메일 소스 수정 권한이 없다는 전제(이전 논의) → 실제로는 어떤 방식(연동 계약, 별도 팝업 연결 등)으로 "탑재"할지 벤더사와 별도 협의 필요 |

**다음 단계로 넘어가기 전에 확인해야 할 대상**
- IT팀 — 사내 표준 기술스택, 인트라넷 서버/인증 연동 가능 여부
- 보안팀 — 보안성 심의 필요 여부, 첨부파일 처리 정책
- 자료교환 프로그램 벤더 — API/폴더감시 기능 추가 가능 여부, 비용·일정
- 웹메일 벤더(또는 사내 운영 부서) — 실제 화면에 기능을 삽입할 수 있는 방법과 권한

→ 이번 3일 프로토타입은 이 미결 항목들을 확인받기 위한 **논의용 자료**로도 활용한다 (동료 반응 테스트 + 위 담당자들에게 "이런 걸 만들고 싶다"를 보여주는 용도 겸용).

## 필요한 학습 개념
| 개념 | 왜 필요한가 |
|---|---|
| HTML 기본 구조와 시맨틱 태그 | 화면을 코드로 옮기는 가장 기초적인 단계 |
| CSS Flexbox | 사이드바+본문, 툴바 버튼 배치 등 지금 화면 레이아웃의 대부분이 flex로 구성됨 |
| CSS 클래스 토글(`classList.add/remove/toggle`) | 화면 전환(A↔D), 모달 열고 닫기, 버튼 활성화/비활성화 구현의 핵심 |
| JavaScript 이벤트(`onclick`, `onchange`) | 체크박스 선택, 버튼 클릭에 반응하는 로직 |
| 배열 다루기 (`forEach`, `unshift`) | "내 전송함" 리스트에 신청 건을 추가하고 렌더링하는 로직 |
| 간단한 상태관리 개념 | 지금은 전역 변수(`requests` 배열) 하나로 화면 간 데이터를 주고받는 원리 이해 |
| Git 기초 (`add`/`commit`/`push`) | 작업 버전을 안전하게 저장하고 GitHub에 올리는 최소한의 사용법 |
| AI 코딩 툴에 프롬프트 작성하는 법 | 코드를 몰라도 "이 버튼을 파란색으로" 같은 요청으로 원하는 결과를 얻는 능력 |
