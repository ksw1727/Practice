# 웹메일 자료전송 기능 — 실제 구축 기획안

## 문제
업무망·외부망이 분리된 환경에서, 메일로 받은 첨부파일을 업무망으로 넘기려면 파일을 다운로드한 뒤 별도의 자료교환 프로그램에 다시 업로드해야 하는 이중 작업이 반복되어 시간이 낭비된다.

## 개발 목표 (MVP)

**핵심 제약**: 현재 자료교환 프로그램은 API도, 폴더감시 기능도 제공하지 않는다. 즉 "파일이 실제로 망을 넘는 과정"을 자동화하는 것은 지금 당장 기술적으로 불가능하다. 이 제약이 풀리기 전까지는 완전 자동 전송을 MVP 범위에 넣을 수 없다.

그래서 Phase 1 MVP는 **"신청 → 승인 → 추적" 워크플로우를 실제 시스템으로 구축하는 것**까지로 범위를 잡는다. 파일의 물리적 이동은 기존 방식(수동 업로드)을 유지하되, 승인되지 않은 건은 업로드할 수 없도록 절차를 강제하여 최소한 "재확인을 위해 왔다갔다 하는 시간"과 "승인 여부를 몰라서 발생하는 재작업"을 없앤다.

| Phase | 범위 |
|---|---|
| **Phase 1 (MVP)** | 특정 부서/팀 파일럿(예: 20~30명)에게 먼저 적용. 웹메일에서 첨부파일 선택 → 전송 신청(반입사유/자료내용 필수 입력) → 승인권자 승인/반려 → 신청자 상태 추적. 파일 업로드 자체는 여전히 사람이 수행 |
| **Phase 2** | 벤더(자료교환 프로그램 제조사) 또는 사내 IT팀과의 협의 결과에 따라, 실제 파일 이동까지 자동화 |
| **Phase 3** | 파일럿 결과를 바탕으로 전사 확대 |

이 범위 확정이 아직 완전하지 않은 이유는, 아래 "결정이 필요한 항목"에 있는 미결 사항들이 실제 개발 착수 전 확인돼야 하기 때문이다.

## 결정이 필요한 항목 (개발 착수 전 필수 확인)

| 항목 | 상태 | 확인 대상 |
|---|---|---|
| 파일이 실제로 망을 넘는 방법 (Phase 2 설계) | 미결 | 자료교환 프로그램 벤더, 사내 IT 인프라팀 |
| 사내 표준 기술스택(언어/프레임워크) 지정 여부 | 확인 필요 | IT팀 |
| 인증 방식(사번 자체 인증 vs 사내 SSO) | 미결 | IT팀 |
| 서버/DB를 둘 인트라넷 환경과 권한 | 미결 | 인프라팀 |
| 보안성 심의 대상 여부 및 절차 | 미결 | 보안팀 |
| 웹메일 화면에 실제로 기능을 삽입할 권한/방법 | 미결 | 웹메일 벤더 또는 운영 부서 |
| 승인권자 지정 로직(자동 vs 수동 지정) | 미결 | 현업 부서 정책 담당 |

이 항목들이 정리되기 전에는 아래 "사용 기술", "환경" 섹션의 내용은 **잠정안**이며, 확인 결과에 따라 변경될 수 있다.

## 화면
| 화면 | 역할 | 사용자 |
|---|---|---|
| A. 메일 읽기 (기존 웹메일 + 체크박스) | 첨부파일 중 전송할 파일 선택 | 신청자(전 직원) |
| B. 전송 신청 폼 | 선택 파일 확인 + 반입사유·자료내용 필수 입력 + 제출 | 신청자 |
| C. 승인자 콘솔 (신규) | 대기 중인 신청 목록 확인, 승인/반려 처리, 반려 시 사유 입력 | 승인권자 |
| D. 내 전송함 | 파일명 / 상태(승인대기·완료·반려) / 신청일시 리스트 | 신청자 |
| E. 반려 상세 | 반려 사유 확인 | 신청자 |
| F. 관리 대시보드 (Phase 2 이후) | 전체 신청 현황, 감사 로그 조회 | 보안팀/관리자 |

**화면 흐름**
```
A(첨부파일 체크) --[전송 신청]--> B(신청 폼 제출)
      --> C(승인권자 확인) --[승인]--> D(신청자: 완료 표시)
                            --[반려]--> D(신청자: 반려 표시) --> E(사유 확인)
```

## 역할
실제 구축은 데모 제작과 달리 실제 개발 역량이 필요하다. 필요한 역할은 다음과 같다.

| 역할 | 담당 업무 |
|---|---|
| 프론트엔드 개발 | 화면 A~F 구현, 웹메일과의 UI 연동 |
| 백엔드/API 개발 | 신청·승인·상태관리 로직, DB 연동 |
| 인증/보안 연동 | 사내 SSO 연동, 권한 체계 설계, 보안팀 협의 대응 |
| 인프라/배포 | 서버 구축, 배포 파이프라인, 벤더·IT 인프라팀 협의 |
| QA/테스트 | 파일럿 배포 전 기능·보안 테스트 |

현재 팀 구성(비개발자 중심)만으로는 이 역할들을 채우기 어려우므로, 실제 개발 착수 전 사내 개발 인력 또는 외부 개발 리소스 확보가 선행되어야 한다.

## 협업 방식
- 2주 단위 스프린트로 진행하며, 매 스프린트 종료 시 동작하는 결과물을 시연한다.
- 형상관리는 사내 정책에 맞는 저장소(사내 GitLab 등, 외부 GitHub 사용 가능 여부는 보안팀 확인 필요)를 사용한다.
- 기능 단위 브랜치 전략 + 코드 리뷰를 거쳐 병합한다.
- IT 인프라팀·보안팀과 주 1회 정기 협의체를 구성해 "결정이 필요한 항목"을 스프린트마다 하나씩 해소해나간다.
- 벤더(자료교환 프로그램 제조사)와의 협의는 별도 채널로 진행하고, Phase 2 착수 조건으로 삼는다.

## 사용 기술 (잠정안 — 사내 표준 확인 후 확정)
| 영역 | 잠정 후보 | 비고 |
|---|---|---|
| 프론트엔드 | React 또는 사내 표준 프레임워크 | IT팀 표준스택 확인 후 결정 |
| 백엔드 | Node.js / Spring Boot 등 사내 표준 언어 | 동일 |
| 데이터베이스 | 사내 표준 RDBMS (Oracle/MySQL/PostgreSQL 등) | 인트라넷 내부 서버에 구축, 외부 SaaS 사용 불가 전제 |
| 인증 | 사내 SSO(SAML/LDAP 등) | 자체 인증으로 갈지 여부는 미결 |
| 알림 | 사내 메신저 또는 메일 서버 연동 | 승인 요청/결과 알림용 |
| 파일 전송(Phase 2) | 벤더 API 신설 또는 IT팀 자체 미들웨어 | "결정이 필요한 항목" 참고 |

## 환경 (폴더 구조 · 준비물)

**저장소 구조 (예시)**
```
프로젝트/
├─ frontend/          화면 A~F 구현
├─ backend/           신청·승인·상태관리 API
├─ infra/             배포 스크립트, 서버 설정
├─ docs/
│   ├─ 기획안.md
│   └─ 결정사항_로그.md   (미결 항목이 확정될 때마다 기록)
└─ .env.example        환경변수 템플릿 (실제 키는 사내 시크릿 관리 도구 사용)
```

**준비물 체크리스트**
- [ ] 사내 개발/스테이징 서버 (인트라넷 내부)
- [ ] DB 인스턴스 및 접속 권한
- [ ] 사내 SSO 연동 키/문서 (인증 방식 확정 후)
- [ ] 보안성 심의 신청 및 통과 문서
- [ ] IT 인프라팀·보안팀 협의체 일정
- [ ] 자료교환 프로그램 벤더 연락 채널 및 계약/협의 문서
- [ ] 형상관리 저장소 (사내 정책에 맞는 것으로, 외부 GitHub 사용 가능 여부 확인)
- [ ] 파일럿 대상 부서 선정 및 사용자 명단

## 필요한 학습 개념
| 개념 | 왜 필요한가 |
|---|---|
| REST API 설계 | 신청·승인·상태조회 기능을 프론트-백엔드 간 주고받는 표준 방식 |
| 인증/인가(SSO, 세션, 토큰) | 사내 인증 시스템과 연동하고 승인권자·신청자 권한을 구분하기 위해 |
| 관계형 데이터베이스 설계 | 신청건, 승인이력, 사용자 정보를 안전하게 저장·조회하기 위한 스키마 설계 |
| 파일 업로드 보안 기본기 | 첨부파일 처리 시 발생할 수 있는 취약점(악성파일, 용량 공격 등) 방어 |
| 감사 로그(Audit Trail) 설계 | 보안 심의·사고 대응을 위해 누가 언제 무엇을 승인/반려했는지 추적 가능해야 함 |
| 온프레미스 배포/운영 기본기 | 외부 클라우드가 아닌 사내 인트라넷 서버에 배포·운영하는 방식 |
| 애자일/스프린트 협업 방식 | 여러 역할이 나눠서 진행하는 실제 개발 프로젝트의 진행 방식 |
